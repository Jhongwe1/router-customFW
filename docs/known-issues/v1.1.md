## 🔴 What `v1.1` does not establish — 2026-10-29 (`P6r-10`, `P6r-11`, `P6r-12`)

`v1.1` is defined by `P6r-10`, `P6r-11` and `P6r-12` (`README.md`'s version map); the gate they belong to,
`P6r`, is still open. Its image is `mainline-495094ab.img`, 1,144,832 bytes, sha256
`a016a5c0354b2350dc72eb67e1a03fd98e457e66d4908487c2c75ce964e2adb8`, `RECIPE_ID` `495094ab`: the shipped shape
of `P6r-10`'s tree, built with `BENCH_SHELL=0`, from `a1dc141c` on 2026-10-24 and again from `c95d3334` on
2026-10-29 in another clone, byte-equal (`SPEC.md` `FW-275`). No signed container is an asset. What the image
is made of is [`docs/sbom.md`](../sbom.md) Appendix C. The ones a reader of this release most needs:

* **The released bytes booted twice, both from RAM, and never from a flash slot.** 量
  `bench/2026-10-25/P12-02-boot` and `P13-02-boot`: `RLXFW-ID0=495094AB`, `bench profile OFF: no shell on
  /dev/console` and `console shell DISABLED in this build`; on a store with no admin password, the console's
  first-password prompt, a password the owner set there off the record, `/api/login` answering 200 with it and
  401 with another (`P12-04`), and no prompt at the next boot (`P13`). Everything else this release adds was
  measured on V (version 6, recipe `e7f77c95`) and U (version 7, recipe `495094ab`), the same code built with
  `BENCH_SHELL=1`. 量 U's initramfs differs from this image's in `/init` alone (101,764 against 124,216
  bytes; the other 16 files are byte-equal), and because the initramfs is linked into the kernel, U's `vmlinux`
  and `System.map` are other bytes too. So these bytes have not booted through `rlxboot`, run their update path,
  loaded a persisted store or advanced the counter.
* **The pin on the uploaded bytes is not in `bench/`.** The bench day ran without cards, by the owner's ruling
  of 2026-10-24, and `looprun` writes no digest into its captures. The sha256 it compared before each of the two
  uploads, `a016a5c0…`, is in the session's command lines — `toram.sh P12 …` and `pc2ram.sh P13 …`, scripts
  that check the file against it before `looprun` checks it again with `--image-sha256` — which the 148th
  segment's `LOG.md` entry quotes.
* **`RLXFW-ID0` names the kernel recipe, not the image.** U, the bench build with the console root shell,
  prints the same `RLXFW-ID0=495094AB`. At boot the two differ in the lines `/init` prints (above); otherwise
  only by sha256.
* **The update path needs `rlxboot`'s new build.** The image learns which slot it booted from the handoff
  `rlxboot` passes at the jump (`config/host-compat/0011`, `kernel/linux-2.6.30/arch/rlx/kernel/rlxfw-boot.c`);
  started any other way it refuses every upload — 量 V booted from RAM refused one at `UPDATE_BEGIN` in 0.06 s
  (`FW-271`). The `rlxboot` that passes it, build `3b7474de`, was written to `0x010000` on 2026-10-24; it is not
  an asset of this release, and its source is in the archive (`src/rlxboot/`). The rescue copy at `0x020000` is
  the older build, so an image it starts has no handoff either: 推, the rescue boot was not run
  (`notes/self-update.md` § 9). Not established either: an update from the WAN side, which rlxfw does not have;
  a secret upload, with no TLS (`P6r-12`'s TLS is ⊘); resistance to root on the device, which can drive the
  install path itself.
* **Persistence: one store in two slots, read at the seatings' writes.** The store's two 4,096-byte slots sit
  in two 64 KiB blocks of the free area `0x2B0000`–`0x3DFFFF`, so no erase grain clears both. 量 on V and U: a
  password set with `cfgstore passwd` survived a cold power cycle (`C1`); a cut during a store write left the
  last complete record loading (`K2`, `seq 44`); with both regions erased the store read `source default` and
  refused every login (`W8`, `W9`). That one erased slot leaves the other loading is read from the final boot
  (`F1-02`, `source slot0 seq 1` with `cfg1` erased), in which the loading slot was written after the erase,
  not before. Not established: wear, and more writes than the seatings'.
* **Rollback is refused from flash, and the floor is permanent.** The counter at `0x3F0000` advances by
  programming bits, to the version of the image `rlxboot` booted, once `lan up` is printed and `brokerd`
  answers. 量 `rlxboot` reads it (`ctr=6` after the advance to 6, `notes/rlxboot.md` D21) and refused
  `v1.0`'s `T.rlxu`, version 5, in slot A with `bad=rollback`. On this unit it reads 7, so `T.rlxu` never boots
  from its flash again and every later container needs version 7 or above. Root on the device can advance it to
  its end and refuse every update (`docs/threat-model.md` `T9`).
* **Power cuts during the new writes: one round per kind.** 量 `K1` cut a slot write — unpaced, the kind an
  update makes — in an erase; `K2` a store write; `K3` the counter's program loop, run on the erase probe's block
  (`FW-270`). After each, a cold boot booted a valid image, the store loaded a complete record and the counter
  read a value from the old to the new. Not established: a cut aimed inside a sub-phase (block 0's erase, the
  header page), which a hand-timed cut cannot aim at; the state block's own behaviour under a cut, only the probe
  block having been cut; more than one cut per kind.
* **The console has no shell, and the loader still comes first.** 量 this image's console runs no shell and
  asks for a first password (8 to 64 bytes, read with echo off: 讀 `src/init/firstpw.c`). Anyone at the serial
  header still reaches the loader's prompt before rlxfw runs, and its `FLW`, `EW` and `EB` write flash without
  authentication (`SPEC.md` `LDR-08`, `LDR-09`). The image also still holds the vendor's `mtd_spi_write` and
  `mtd_spi_erase` (讀 its `System.map`), besides rlxfw's own install path.
* **Booted from RAM, the image still writes flash when a setting is stored.** Unlike `v1.0`'s, this image
  carries a write path (`CONFIG_MTD_RTL819X_WRITE=y`). Setting the first password, or any setting, erases and
  programs one of the store's two 64 KiB blocks, `0x3C0000` and `0x3D0000` — 量 the owner's first password at
  `P12` was written as slot 0, `seq 1`. On this unit both blocks read erased in its vendor state (the 2026-08-16
  dump, `notes/self-update.md` § 2.1); on another unit, or another vendor version, they may hold the vendor's
  data. Booted from RAM it refuses every update and does not advance the counter (量 `R6`, `ctr_attempts 0`).
* **Entropy waits for traffic.** 量 with no host traffic for 305 s after a flash boot the pool read 0 and
  `cfgstore passwd` refused (`FW-272`); a password set or a login on a quiet network waits for packets. The
  entropy result is still accounting, not strength (`FW-180`).
* **After a RAM boot a ping flood lost packets; after a flash boot it did not.** 量 6,000 `ping -f`: 0 lost
  on four flash boots, 18.87 % and 8.58 % on two RAM boots, one of them this image's (`FW-273`). Whether the
  boot path or the time since boot decides it is undetermined.
* **Open from the design's own list**: `brokerd`'s reload cost per request, the image's growth against the
  design's estimate, and `MemFree` while `brokerd` holds a staged upload (`notes/self-update.md` § 9, items 5, 8
  and 9).
* **The corresponding source.** The archive is built from the release commit by `tools/srcarchive.py`
  (`docs/release-process.md`). `REPRODUCE.md`'s three layers were run on `v1.0`'s archive, not on this one; 量
  this image rebuilt byte for byte from `c95d3334` in a fresh clone, on the machine that built it (`FW-275`).
  The two gaps are unchanged: no pinned tree holds the source of `libgcc.a` (`SBOM-4`), and the archive does not
  stage iperf3's tarball (`SBOM-3`).
* **Carried from `v1.0`, unchanged** ([its list](v1.0.md)): one unit and one loader build; no TLS; no WAN —
  switch ports 0–5, the jack labelled WAN among them, in one VLAN; the WLAN driver is the vendor's; none of it is
  secure boot; booted from flash, the Ethernet rests on a write set shown sufficient, not necessary; the ramfs
  mounts have no size limit (讀 `src/init/mounts.c`); `R9`'s table does not say rlxfw is more secure; the
  bring-up report's power tree is a desk reconstruction and no interrupt latency was taken by logic analyser
  (`LA-1`, ⊘); `iperf3` rebuilds to the shipped bytes only at its first build path; the tag is unsigned.
* **Flash, since `v1.0`.** The bench day of 2026-10-24 and 25 wrote fourteen sets — `rlxboot` at `0x010000`,
  slots A and B, the store's two regions, the counter's state block and the erase probe's block — each named
  before the write and made after the owner's yes at the bench; no `FLW`, `EW`, `EB`, non-zero `AUTOBURN` or
  `FLR` was issued. Every slot and `rlxboot` write was bracketed by digest maps of the flash in 128 KiB groups,
  and between the two maps only what it wrote changed; at the `rlxboot` write, inside the group that also holds
  the loader, only the units at `0x010000`–`0x014FFF` (the 147th segment's `LOG.md` entry). What none of it
  sees: two writes that cancel. The `FLR` bracket stays at 1,024 of 4,194,304 bytes.

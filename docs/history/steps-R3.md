## `R3`'s step list — ✅ CLOSED 2026-08-31, kept as written

**Written 2026-08-28 on entering the gate, before any of it was done.** Budget
**猜, uncalibrated: 12 steps.** The gate board says 12 and `plan/` §12.1 says 13
(8 desk + 4 bench + 1 instrument). Neither is calibrated and the difference is
not worth resolving before the first step reports. **Four of the twelve are at
the bench and they are not four seatings** — `R1h-3` shares the first one, and
`probe3` runs first inside it.

🔴 **This gate is the first one whose DoD is a sentence about the device rather
than about a file, and that is why it is decomposed before it is attempted.**
*"My kernel boots to a shell and pings"* reads as one claim and is five, each
with its own observable and its own way of being faked.

### The DoD, split into what can be refuted

| | claim | the observable | what refutes it |
|:-:|---|---|---|
| **D1** | the image is delivered and entered | `---Jump to address=80500000` followed by output that is **not** the loader's | silence after the jump line — which is two causes, not one (`RUNSHEET` §B3 says so already) |
| **D2** | the decompressor runs and the kernel is entered | `Linux version 2.6.30.9 (<me>@<host>) … <date>` | the banner is the vendor's build stamp → **the vendor kernel booted, not mine** (see the anti-DoD below); or output stops inside the decompressor |
| **D3** | early bring-up completes | `MemTotal:` printed, and the console echoes | a panic before `start_kernel`, or a hang with no further output — the case the plan calls *memory-related*, and where it also says the DRAM is the loader's so the suspect is the map or the cache setup |
| **D4** | userspace is reached and the shell accepts typing | a prompt, **and a typed command returns output** | `Kernel panic - not syncing: No init found`, or a prompt that does not echo |
| **D5** | it pings | `ping -c 4` from the board gets ≥ 1 reply **and** the host's capture shows the echo request | replies with no host-side capture = something else answered; host-side requests with no replies = the driver transmits and does not receive |

🔴 **The anti-DoD, and it is written first because this project has already been
caught by it.** 2026-08-25, `R1g-4b`: *a second `J 80500000` booted the vendor
kernel*, because **the loader re-stages `0x80500000` on a watchdog reset**. So a
banner is not evidence that my kernel ran. **Every pass criterion below carries a
discriminator the vendor image cannot produce**: the `(user@host)` and date in
`Linux version`, plus one string emitted by code that exists only in my tree.
A capture without that string is recorded as *unattributed*, never as a pass.

### The two decisions this gate opens with, both made at `R3-0`

**Decision A — `R3` builds with `rsdk-1.3.6-4181`, through its own wrapper.**
It fills the half of `TC-05` that was left blank.

1. 讀 `TC-14`: it is the **only wrapper on hand that accepts `-march=4181`**, and
   `boards/rtl8196e/config.in` is `ARCH_CPU_RLX4181=y`.
2. 讀 `TC-15`: `{4180, 4181, 5181, mips1}` is the side that exposes the load delay
   slot and gets the padding; one `vmlinux` from one source through
   `rsdk-1.5.5`'s wrapper carries **21,185** load-use violations. That is a
   disqualification, not a preference.
3. 讀 `TC-17`: the drop's own top-level `.config` selects this release for this
   board.
4. 讀 `TC-16`: it is one of two toolchains that has linked a **complete
   `vmlinux`** for this board, rc=0 — and the other one is the one point 2
   disqualifies.
5. 🔴 **The objection that does NOT carry over, said plainly so the decision is
   not defended with it.** The reason to fear `rsdk-1.5.5` driving `-march=4181`
   is that its uClibc and crt are 5281-built and put three load-use violations
   into every program's entry path (`notes/rebuild-vs-shipped.md` §4). **A kernel
   links neither.** What is left against that route is that its flag set is a
   **reconstruction (推)** rather than a reading, and that is enough on its own:
   if `R3` does not boot, the vendor's own (toolchain, board, config) triple
   leaves the code generator out of the suspect list, and a reconstructed
   toolchain puts it back in.

**Decision B — the first boot mounts an initramfs built from this unit's own
userspace, not the flash rootfs.**

1. 🔴 **Safety dominates on a one-device project.** ~~An initramfs boot never
   instantiates an MTD partition map.~~ 🔴 **REFUTED on the device, 2026-08-29.**
   量, `bench/2026-08-30b/L3.log`: the `loud` boot created **two** MTD
   partitions, and the first spans `0x000000–0x130000`, which **contains both
   regions `CLAUDE.md` forbids**. Nothing was written and the decision still
   stands — on its other three legs, which were always the stronger ones — but
   **the safety margin this leg claimed was never there.** `notes/kernel-build.md`
   §16 owns the reading. *(Kept as written, because a decision's stated reason is
   worth more when it can be read against what happened.)* The flash-root route needs me to author
   one, and the two regions `CLAUDE.md` forbids — `0x000000–0x005FFF` and
   `0x006000–0x007FFF` — are inside the part a wrong map covers. 讀:
   `rtkload/Makefile` computes `FLASH_OFFSET=30000` under `CONFIG_RTL_819X`
   while this unit's kernel header is at flash `0x060000`, so **the drop's layout
   is already known not to be this unit's** and the map would be new work rather
   than reuse.
2. 讀: it is **the vendor's own supported path**, not an exotic one —
   `boards/rtl8196e/Makefile`'s header is *"Build instructions for Realtek RLXOCP
   with initramfs"* and `rtkload/Makefile` branches on `CONFIG_BLK_DEV_INITRD`.
3. **It keeps userspace as a controlled variable instead of removing it.** The
   contents are this unit's own binaries, unmodified. If the shell does not come
   up, the shell is not the new thing. Writing my own `init` would add a
   variable; the drop's `root.bin` would add three (different SDK generation,
   different model, not this unit's `H601`).
4. The plan's own stop-loss for this gate is *swap to an initramfs to halve the
   variables*. Starting there spends the halving instead of holding it, and what
   is held in reserve becomes the flash root — the **closer-to-vendor**
   direction, which is the better second experiment rather than the better first.

⚠️ **And Decision B has an arithmetic precondition that is checked before the
bench, not at it.** The image is entered at `0x80500000` and the kernel
decompresses to `0x80000000`, so the decompressed image must end below
`0x80500000` or the decompressor overwrites its own input: **5,242,880 bytes is
the ceiling.** This unit's decompressed kernel is 3,374,772 (量), leaving
**1,868,108 bytes** for everything the initramfs adds. If it does not fit, the
answer is not a smaller initramfs first — it is `LOAD_START_ADDR=0x80A00000`,
which `rtkload/Makefile` already supports for other boards and which `G0` has
already probed on this device.

### 🆕 The running order, which is NOT the step numbering, and why

**Written 2026-08-28 before `R3-4` was started, and it holds.** The steps are
executed **`R3-4` → `R3-5` → then back to `R3-2`'s stages 3–6**,
not in numeric order.

**The reason is that stages 3–6 build an image out of a kernel that does not
exist yet.** `R3-2` verified the pipeline's first two stages against the
vendor's own intermediates, which is what made it an instrument. Stages 3–6
— LZMA, `cvimg vmlinuxhdr`, the link at `LOAD_START_ADDR`, `nfjrom` —
consume **the** `vmlinux`, and the `vmlinux` `R3` will upload is the one `R3-4`
configures and `R3-5` fills. Running `nfjrom` first would have produced an
artefact that had to be thrown away and re-derived, and — worse — a
set of sizes and sha256s in the write-up that described a file nobody would ever
upload.

量 2026-08-28, and this is why it was not a close call: the `vmlinux` at the end of today is
**3,968,113** bytes where `R3-2` measured **3,340,287** — **627,826 bytes** of
difference, from `R3-4`'s flag (+33,248 on the file) and `R3-5`'s initramfs
(+594,578, of which 584,704 is the cpio in `.init.ramfs`). Every size and sha256 that
stages 3–6 would have produced this morning describes a file nobody will upload.

⚠️ The first version of this paragraph added `.text`'s +16,788 to the cpio's
584,704 and called the total 627,826. Those are a section delta and a file delta
and they do not add up to a file delta; the two file deltas above do.

⚠️ **What this costs**: `R3-2` stays half-done for one more step, so
`TC-d`'s image half is still open and `K4` in `notes/kernel-build.md` is
satisfied only for stages 1 and 2. That is recorded as a debt, not as a pass.
